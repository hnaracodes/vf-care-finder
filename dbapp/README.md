# dbapp: the care finder as a Databricks App

This folder is what gets deployed. `server.py`, `app.yaml`, `requirements.txt` and `static/` belong to WP8. `bundle/` and `vf/` are generated by `scripts/wp12_bundle.py` (WP12): do not edit them by hand.

- `bundle/`: the data the app loads at start (contract: `docs/07_data_contracts.md`, "The app bundle"). Built at deploy time, not committed. Only `bundle/manifest.json` is versioned, as the local reference the Databricks run is compared with.
- `vf/`: a copy of `src/vf`, so the app runs the tested code. Regenerate it with the bundle script after any change to `src/vf`. Before any deploy, `.venv/bin/python scripts/wp12_bundle.py --check` exits 1 if `dbapp/vf` differs from `src/vf` or the bundle was built from older gold grades.
- Grades: the app serves WP4's student grades (`method: student`, model `student_1b`, on `ob_delivery`, `h24`, `icu`, `ventilator`; regex v0.2 on the other tags). The Databricks notebook makes the same grades by applying the same saved model, not by retraining it (see "Deploy: pipeline on Databricks").

## Deploy: pipeline on Databricks (the brief's "run on Databricks")

0. Stage the one git-ignored input the notebook needs: WP4's fitted student model. The notebook applies it to the tags it ships, so the Databricks grades come from the same model as the local ones. Its training data (LLM teacher labels) stays local. Once, and again after WP4 retrains:

   ```bash
   databricks schemas create vf_datathon workspace                  # "already exists" is fine
   databricks volumes create workspace vf_datathon pipeline MANAGED # likewise
   databricks fs mkdir dbfs:/Volumes/workspace/vf_datathon/pipeline/inputs
   databricks fs cp data/models/wp4_student/student_1b.pkl \
     dbfs:/Volumes/workspace/vf_datathon/pipeline/inputs/student_1b.pkl --overwrite
   ```

   Rebuild the bundle locally first (`.venv/bin/python scripts/wp12_bundle.py`): the notebook reads the shipped tags and the model's sha256 from `dbapp/bundle/manifest.json` (`grade_source`), and refuses a model whose checksum differs.

1. Upload the repo to your workspace. `databricks sync` skips what `.gitignore` lists (the deploy docs give `.gitignore` as the way to exclude files), so `data/`, `.venv/` and `node_modules/` stay local. Look at the dry run first:

   ```bash
   databricks sync --dry-run --full . "/Workspace/Users/$ME/cmu-datathon"
   databricks sync --full . "/Workspace/Users/$ME/cmu-datathon"
   ```

2. In the workspace, open `cmu-datathon/notebooks/01_pipeline`, attach serverless compute, check the widgets (catalog and schema names), and choose Run all. Or run it as a one-time serverless job from the CLI: `databricks jobs submit --json '{"run_name":"vf-pipeline","tasks":[{"task_key":"p","notebook_task":{"notebook_path":"/Workspace/Users/'$ME'/cmu-datathon/notebooks/01_pipeline","source":"WORKSPACE"}}]}'`. The notebook:
   - compares the Marketplace tables with the local export (row counts, columns, `null` cells, rows with NUL bytes), side by side;
   - runs WP1, WP2 Part A and B, WP3 (regex), WP4 (applies the staged student model with `wp12_bundle.apply_student`) and WP11 (with `--no-scenarios`: the scenario impact is a report-only number that needs the git-ignored `scenarios.csv`, and it changes no flag) through `vf.io`'s Databricks source. A failing step is reported and the rest still run;
   - prints every bundle and pipeline count next to the local run's `manifest.json`: the shipped (student) grades, and separately the regex v0.2 grades from WP3. Any difference is a bug to explain;
   - writes `dbapp/bundle/` and `dbapp/vf/` into the uploaded repo folder only when every step passed and the grades came from the same model as the local run (widget 8, `publish_bundle`, default `if_ok`). Otherwise it says why and leaves the repo folder alone: do not deploy from it then. The copied bundle has no `.gitignore`;
   - saves Delta tables `facilities_silver`, `facts_silver`, `capability_grades`, `facility_flags`, `places` in `workspace.vf_datathon` (widgets 3 and 4);
   - fails the run at the end if any step failed.

   Do not run `databricks sync` again between this step and the deploy: it would put the local `bundle/manifest.json` over the one the notebook wrote. To update code after the run, import single files with `databricks workspace import`, or rerun the notebook.

3. Create the app (first time only). Creating it also starts its compute:

   ```bash
   databricks apps create "$APP" --description "Find the right care: cited facility answers with stated uncertainty"
   ```

4. Deploy from the uploaded folder:

   ```bash
   databricks apps deploy "$APP" --source-code-path "/Workspace/Users/$ME/cmu-datathon/dbapp"
   ```

5. Wait for the deploy to succeed, then read the URL:

   ```bash
   databricks apps get "$APP" -o json | jq '{url, app_status, compute_status}'
   ```

6. Open the URL, run the brief's five scenarios, and write the URL at the top of this file.

## Deploy: bundle built locally (faster, for a quick redeploy)

Use this when the local pipeline outputs are current and you only want the app updated.

```bash
.venv/bin/python scripts/wp12_bundle.py --stage /tmp/vf_app   # builds dbapp/bundle and dbapp/vf, then copies dbapp/
                                                              # to /tmp/vf_app without .gitignore files and caches
databricks workspace delete --recursive "/Workspace/Users/$ME/vf-care-finder"   # skip on the first deploy
databricks workspace import-dir /tmp/vf_app "/Workspace/Users/$ME/vf-care-finder"
databricks apps deploy "$APP" --source-code-path "/Workspace/Users/$ME/vf-care-finder"
```

`import-dir` is used here, not `sync`, because `bundle/` is git-ignored and `import-dir` skips only `.git`, `.databricks` and `node_modules` (`databricks workspace import-dir --help`). The staged copy has no `.gitignore`, so whether `apps deploy` reads one does not matter. The delete first is because `--overwrite` replaces files but does not remove ones a rebuild dropped.

## Restart before judging (D034)

On Free Edition an app runs for up to 24 hours after it was started, updated or redeployed, then stops on its own. Restart it shortly before anyone judges it:

```bash
databricks apps get "$APP" -o json | jq '{app_status, compute_status, url}'   # is it running?
databricks apps stop "$APP"                                                    # then start again,
databricks apps start "$APP"                                                   # which restarts the 24-hour clock
```

If it is already stopped, `databricks apps start "$APP"` is enough. Redeploying (step 4) also restarts the clock. Then open the URL once and run "dialysis near Jaipur" to confirm it answers.

If it does not come up:

```bash
databricks apps logs "$APP" --tail-lines 300            # app and system logs
databricks apps list-deployments "$APP"                  # did the last deploy succeed?
```

## Limits that bite

- **10 MB per file.** "App files can't exceed 10 MB. If any file in the app directory exceeds this limit, deployment fails with an error." Since D043 the keyword matrix is saved in parts (`matrix.part-NNN.npz`). Build of Nov 21 late evening: 45.8 MB in all, 42 files in `dbapp/`, largest `bundle/places.parquet` at 6.8 MB, nothing over the limit. The bundle script reports any file over the limit and exits 1.
- **`bundle/.gitignore` says `*`.** It keeps the bundle out of git. `databricks sync` honours it, nested files included (checked with `sync --dry-run`, Nov 21: only `bundle/.gitignore` and `bundle/manifest.json` upload), so the pipeline route rebuilds the bundle in the workspace. The deploy docs do not say whether `apps deploy` reads `.gitignore` files, so neither deploy route ships one: the notebook copies the bundle without it, and `--stage` leaves it out. After every deploy, still check that `/api/health` shows `mode: bundle`.
- **Pinned libraries in the notebook.** The notebook installs the same versions as `requirements.txt` (pandas 3.1.1, pyarrow 26.0.1, numpy 2.4.6, scipy 1.17.1, scikit-learn 1.9.1, rapidfuzz 3.14.6). The serverless default on Nov 21 was Python 3.11.10 with pandas 1.5.3, and that breaks the pipeline: three fact texts hold a NUL character (JSON `\u0000` escapes inside the raw lists, so `vf.io` keeps them as text), pandas 1.5's string hashing stops at NUL, and WP3 fails with `'float' object is not iterable`. pip warns that `databricks-connect 15.4.26` wants numpy<2, pandas<3 and pyarrow<25; `toPandas()` still worked under the pins (checked Nov 21). scikit-learn must stay the version that pickled the student and the keyword index.
- **Pickled vectorizer.** `bundle/keyword_index/vectorizer.pkl` was written with scikit-learn 1.9.1 and numpy 2.5.5 (local), and it loads under the pinned 1.9.1 and 2.4.6 on Python 3.11 (checked). Keep `scikit-learn` pinned to the version that built the bundle.
- **Up to 3 apps per account**, serverless compute only, and outbound internet from serverless is limited to trusted domains. The notebook installs one package with `%pip` (`rapidfuzz`) and calls no external API.
- **Do not share the app outside the workspace.** The facilities table's reuse terms are unchecked. Changing app permissions beyond your workspace is a public step: prepare it and ask Hruday.
